### 2.7 上板两个 bug 修复后复核（check_Runs，MultiSeed seed 2 / seed 3，2026-10-29）

上板反馈两处故障：① 上电后 TF 卡 WAV 不播，只有系统测试音；② 视频层有画面但整段错位、音频明显异常、卡到播不完。

**bug1 根因（已用卡上文件核对）**：卡内 `sample-speech-5m.wav` 为 16bit/44.1k 单声道，但 fmt(16) 之后紧跟 26 字节 `LIST/INFO` 块，`data` 起点在文件偏移 **70**。旧解析器用 `pbyte[1:0]` 判断 chunk 对齐，隐含“所有 chunk 4 字节对齐”的前提；26 字节的 LIST 让后续 ID 落在 2 字节相位上，`data` 永远认不出来 → `wav_ok` 不成立 → 回退测试音。

修复 `SD/sd_card_wav.v`：ID/SIZE 各自用独立计数器识别 chunk 边界，奇数长度 chunk 补 `P_PAD` 对齐字节，32bit 字段统一按小端移位装配，找到 `data` 后冻结解析（避免 payload 被误判成 chunk 头）。同时把解析输入打一拍（`pdata/pvalid`）切断“扇区长比较 → 解析器 → 字段寄存器”的组合链。

**bug2 根因 a（总线交接）**：`sd_card_bmp` 里视频客户端的归属信号直接取 `i_video_play`，而该信号由 `video_frame_fill` 的组合状态给出，可在 BMP 扇区中途拉高。切换瞬间视频客户端收到的是在途 BMP 扇区的尾部字节，逐字节计数错位 → EGV 图像整段错位、音轨字节全部错乱；同时 BMP 装载被视频请求打断，帧读取窗口被挤压 → 卡顿播不完。

**bug2 根因 b（段表计数器溢出）**：`egv_reader` 的“本段剩余扇区数”只有 16 位，`RUN_MAX = 16'h4000`，而本容器 run1 实际 **385,024 扇区**，被饱和成 16,384。播放到逻辑扇区 16,639（约 3.4 秒）时误判“本段结束”，物理地址从 529,665 直接跳到 `RP2 = 905216`，此后一直读容器外的数据 → 画面错位、音轨全错、数据量不够导致播不到结尾。用旧 RTL 复现的回归证据：`CNT ERR g=16482 got 157 exp 201`、`ADDR ERR g=16639 got 905216 exp 529664`。

修复：视频客户端改为**只在扇区边界接管总线**（`egv_owns_r` + `bus_idle`：BMP/WAV 均无在途扇区才交出，撤销时等当前批次结束）；`sd_card_sec_read_write.v` 读数据/有效/结束统一打一拍并新增 `S_READ_WAIT`，保证客户端仍有一拍时间更新下一扇区地址（否则单块读会读到旧 LBA）。`sd_card_cmd.v` 的 CMD18 支持一次请求连续读 N 个扇区，视频帧 201 个扇区不再逐块发命令。`egv_reader` 的段计数器扩到 **20 位**（上限 1,048,575 扇区，覆盖任意单段），段长由 `EGV_RG*` 直接做常量，不再饱和成 16K。

### 2.8 读核地址锁存过早导致 LOADING 卡死 / 视频黑屏（2026-10-29）

上板 `avfix2` bit 后：开机一直停在 `LOADING IMAGE`，等多久都不出图；SW3 拉高进视频层永久黑屏。

**根因**：`sd_card_sec_read_write` 在 `S_WAIT_READ_WRITE` 里用 `sec_addr <= sd_sec_read_addr` 采样下一个请求，但它离开 `S_READ_END` 后只空等了 **1** 拍（`S_READ_WAIT`）就采样。而本轮的时序修复给结束脉冲加了两级寄存——`sec_end_pulse → rd_end_q`（读核内）`→ bmp_e_q`（`sd_card_bmp`）——客户端因此要等到第 3 拍才更新 `sd_sec_read_addr`。核心早一拍锁存，拿到的永远是**上一个**扇区号：

```
每个扇区都重发上一条 CMD17 → 扫描永远停在扇区 0 → 认不出 BMP 头 → img_found_count=0
                                                                 → 常显 LOADING IMAGE
```

### 2.9 上电仍出测试音 / 视频层错位卡死（WAV 24/32bit + EGV 运行时段表，2026-10-31）

### 2.11 画面横向循环错位/彩条（视频写口带宽过载）、末帧冻结、菜单按键说明（2026-11-01 上板反馈）

上板 `wavfix` bit 后用户反馈：① 视频能流畅播放但画面有错位彩条（黑底大量彩条），整体画面右侧约 3/4 跑到左侧、左侧 1/4 跑到右侧（横向循环移位）；② 播几秒后画面停住，资源面板 `FRAM` 停在 `01928` 不变而 `VIDEO` 仍显示 `RUN`，K1 两次后从彩条重播，`FRAM` 增到 `03856` 又停；③ 视频音轨"一直刺啦刺啦"；④ 菜单右侧开关/按键说明与实物不符。

#### 根因 1：`video_frame_fill` 视频写口没有节拍门控（画面错位 + 彩条）

`E_ROWW / E_RD / E_W0 / E_W1` 四个状态直接裸推进，只有 `step`（4 拍一字节拍器）参与 `p`/`phase` 的计数判定，状态迁移本身不受门控 → 实际是 **2 拍出 2 字**（约 67M 字/s ≈ 400MB/s），叠加显示读口 25M 字/s 后 SDRAM 带宽翻倍过载。写侧 FIFO 溢出丢字，每行内容整体前移固定字数，正好表现为"右边 3/4 跑到左边"的横向循环移位；丢字点随机化后行内颜色错位即为彩条。

修复：四个状态全部加 `if (step)` 门控，写口回到严格 4 拍一字（约 21M 字/s）。一帧 296 行 = 189440 字约 11.4ms 写完，远小于 41.67ms 帧周期，带宽余量充足。该行代码有醒目注释，**不得去掉 `step` 门控**。

#### 根因 2：`FRAM` 停在 01928 是"播完即冻结"的设计行为

`EGV_FRAMES=1928`，播完最后一帧后 `egv_reader` 置 `eof_stop` 停止取流、画面冻结在末帧；但 `VIDEO:RUN` 取自 `vid_on_v = vid_layer_v & vid_play_v`，不反映 EOF，于是"面板显示 RUN 但画面不动"被误认为卡死；01928→03856 正是第二遍播完（1928×2）。

#### 根因 3：菜单右侧说明与 `ctrl.v` 不符

### 2.12 彩条/横向错位/电音/启动满屏彩电（2026-11-01 第二次上板反馈）

上一轮 `step` 门控修好后上板复验，用户反馈现象**依旧**，并补充了三个关键量：

1. 源视频 81 秒，开发板**不到 60 秒就回卷重播**；
2. 画面横向错位是**固定比例**（目测 1/5~1/4，前后一致，不随播放推进变化）；
3. 启动即**满屏彩条 + 电音**，几秒后变**满屏彩电**，随后才开始播放带彩条/错位的画面，播 50 余秒后重复这一序列。

#### 结论先行：三条症状同源，都是"每帧实际读到的扇区数不足"

把三条现象放在一起，只有一种解释能同时成立：

| 现象 | 机制 |
|---|---|
| 固定横向错位 | 视频流少了整数个扇区 = 512B = 256 源像素 = **512 显示像素的循环左移**，且每帧少同样的量 → 偏移量恒定，正好是"左边一截跑到右边" |
| 不到 60 秒就回卷 | `i_sd_read_end` 提前到来 → `sec_i` 比真实扇区跑得快 → 帧提前判满 → 帧周期缩短（约 26~33ms）、总时长按比例缩短 |
| 持续电音 | 帧提前结束 ⇒ 每帧音频字节同样缺失 ⇒ 48kHz 供给断续/溢出，ASRC 拿到不连续样本 → 宽带噪声（"电流声"），而非音调变化 |
| 启动满屏彩电 | 见下面独立的门控缺陷 |

> 关键交叉验证：**201 扇区 / 25MHz SPI 的纯传输时间就要 32.9ms**，而"1928 帧 50 余秒播完"折合每帧约 26ms——**比纯传输时间还短**，物理上只可能是没读满 201 个扇区。

#### 根因 A：CMD18 流式读 + CMD12 终止的批次机制太脆

原来的读法是"一次 CMD18 连续读 201 扇区，读完发 CMD12 终止"。这条链上有三处隐含假设，任何一处错拍都表现为"少读扇区"：

1. **两套 `sec_left` 必须严格同步**：`sd_card_cmd` 里 `sec_left = block_read_secs-1`（判断何时发 CMD12），`sd_card_sec_read_write` 里 `sec_left = sd_sec_read_count`（判断何时撤 `block_read_req`），而 `block_read_secs` 是**组合直连** reader 的 `o_sd_count`——这个值在批内会被逐扇区递减。
2. **最后一个扇区不走 `S_READ_ACK`**：`state <= (stream_rd && sec_left==0) ? S_STOP_CMD : S_READ_ACK;` 末扇区直接跳 CMD12，它的 ack 依赖 `S_STOP_BUSY → S_READ_ACK` 补发；`S_STOP_BUSY` 又有"64 字节仍忙则放弃"的超时兜底。
3. **流终止后卡仍在吐残片**：`S_STOP_CMD` 注释已写明"发送期间完全无视 DO——流模式下卡还在往外吐数据残片"，靠等 `0xFF` 收尾。

三者叠加，一旦节拍不利就会出现"ack 早到/晚到"，`i_sd_read_end` 与真实扇区边界错开 → 计数超前 → 每帧少读若干扇区。

**修复：改成逐扇区 CMD17 独立事务。** `o_sd_count` 恒为 1，每个扇区一次完整事务（CS 每扇区抬起），扇区边界由卡的数据令牌确定，不存在批次计数、不存在 CMD12 终止、不存在残片。顺带把因此失效的 `batch_s/batch_n/run_rem_n_q/rem_n_s_q/sat16` 一并删除。

代价：每扇区约 10~20 字节命令开销，201 扇区约 +1ms；一帧预算 41.67ms，实测仍在 34~36ms，余量足够。

#### 根因 B：视频层未就绪时把 SDRAM 原始内容当画面

```verilog
assign vout_data = (display_valid_s2 | vid_show) ? vout_data_raw : 24'd0;
```

`display_valid_s2` 是图片层的"已提交"标志，BMP 装载完成后**恒为 1**。于是拨到视频层（SW3）而视频缓冲还没被写过的瞬间，`vout_data_raw` 取的是 `rd_addr_idx_mux` 指向的 BUF2/BUF3 —— **SDRAM 里还没初始化的原始内容，就是满屏彩电**。

修复：

```verilog
// 视频层选中时只认 vid_show（视频缓冲已就绪），不再并上图片层标志
assign vout_data = (vid_layer_v ? vid_show : display_valid_s2) ? vout_data_raw : 24'd0;
```

#### 根因 C（加固）：坏帧不再上屏

即使 SD 偶发丢字节，也不该把花屏帧显示出来。`video_frame_fill` 新增帧完整性校验：

- 帧起点清零 `pix_cnt`，每个 `i_pix_en` 累加；
- `E_END` 时 `frame_ok <= (pix_cnt == SRC_W*SRC_H)`（320×148 = 47360）；
- 只有 `frame_ok` 为 1 才切换 `o_disp_bank` 并发 `o_frame_end`。

效果：坏帧内容虽已写进 SDRAM，但不切显示缓冲，屏幕保持上一帧。同时**`FRAM` 计数（资源面板帧号）只在完整帧才递增，因此"FRAM 是否稳定递增"就是一个现成的 SD 数据正确性指示灯**。

### 2.13 无画面/FRAM 按 K1 才 +1/错位依旧（2026-11-01 第三次上板反馈）

上一轮改成逐扇区 CMD17 并加坏帧校验后上板，用户反馈：**按下 K1 完全无画面**，只有按下的瞬间闪一下花屏，`FRAM` 每按一次 K1 才 +1，横向错位依旧。

#### 根因 A：`i_fill_ready` 与 `E_ROWW` 双向死锁（本轮新引入，已修）

```verilog
wire frame_start_now = (st == S_FWAIT) && i_play && !stop_req && i_fill_ready && ...
```

`i_fill_ready` 来自 `video_frame_fill.o_frame_ready`，而它**只在 `E_IDLE` 为 1**。一旦某帧像素不足 47360（SD 丢字节），vf 就卡在 `E_ROWW` 等 `f_row > e_row`，reader 又在 `S_FWAIT` 等 `i_fill_ready`——两者互等，永久停滞。`FRAM` 只在 K1 重新起播（复位状态机）时推进一帧，然后再次卡住，完全对应实测现象。

修复：

| 改动 | 说明 |
|---|---|
| 新增 `E_PAD` 状态 + `wcnt` | 像素不足时补零写满 `VIDEO_WORDS`，保证 `frame_fifo_write` 按时完成、`fin_edge` 正常到来 |
| `E_ROWW` 停滞超时 | 连续等待超 5ms 直接进 `E_PAD`，不再无限等 |
| 坏帧不再阻塞切换 | 之前用 `frame_ok` 阻挡 `o_disp_bank`，SD 持续丢字节时变成永久黑屏；现在坏帧照常上屏，`frame_ok` 仅作统计 |

> 实现细节：`stall_t` 必须是**单次等待**计时。首版写成整帧累计，而"填一行 220us / 输出一行 38us"意味着一帧 296 次等待累计可达 65ms，远超 5ms 阈值，导致每帧只填到第 61 行就补零——这个缺陷被 `e2e_video` 回归立刻抓出（`words=189440` 但 `pix=19477`），已改为在成功转入 `E_RD` 时清零。

#### 根因 B：错位不在数字链路——真实卡数据端到端反证

本轮首次用**卡上真实容器头 + 真实段表**驱动 `egv_reader`（新增 `sim/tb_real_reader.v`）：

- 激励 `real_mem.hex`：`F:/VIDEO.EGV` 前 416 扇区原始字节；
- 期望 `real_exp_pix.hex`：按"跳过 512B 头 + `i%12==11` 为音频 + 跨段跳物理起点"推出的前 2 帧共 94720 个 RGB565 像素。

结果 **`TB_REAL_READER PASS`，零像素错误**，且物理地址序列为：

```
47360(头) -> 47361(数据首扇区) -> 47362 ... -> 47615 --跳段--> 513280 ... -> 513481
```

卡上段表（偏移 44，每段 `(logical, nsec, phys)`）：

| 段 | nsec | phys |
|---|---|---|
| 0 | 256 | 47360 |
| 1 | 385024 | 513280 |
| 2 | 2249 | 905216 |

三者和 387529 = 文件总扇区数；`run0` 含 512B 头，运行时解析已做 `phys+1 / nsec-1`（`rt_rp[0] <= h_val + 1`、`rt_len[0] <= sat20(h_val) - 1`），与封装脚本 `write_cfg_vh` 的 `rp = phys + (1 if i==0 else 0)` 一致。

**由此可以确定：**

| 环节 | 验证方式 | 结论 |
|---|---|---|
| 卡上容器/段表/音视频抽取相位 | Python 按 reader 逻辑独立复现并渲染帧 0/1 | 画面居中正常，无错位 |
| 运行时段表解析 + 物理地址推进 + 跨段 | `tb_real_reader`（真实头+真实段表+2 帧） | 94720 像素全对，地址序列正确 |
| 像素→2 倍放大→写口字流 | `tb_e2e_video` | words=189440 / pix=47363 / aud=8000 全对 |
| SDRAM 缓冲基址与偏移 | 常量复核 | `BUF2=614400`、`BUF3=921600`、`VID_TOP_OFF=58880=92×640`、`BUF3+307200=1228800 < 2^21` |

**即：从 SD 字节流到 SDRAM 写地址，每一个可仿真环节都已证明正确。** 剩余唯一变量是"卡上实际读回的字节是否等于文件内容"，属 SD 物理层（SPI 采样余量 / 触点接触）。

`SPI_HIGH_SPEED_DIV = 0` → SPI = 100MHz/((0+2)×2) = **25MHz**，每 bit 仅 4 个 100MHz 拍，`spi_master` 在 DCLK 翻转同一拍采样 MISO，建立时间约 2 拍（20ns），对 SD 卡 Tco（≤15ns）加线延迟余量仅约 5ns。这是 25MHz 下"确定性读错字节"的典型成因。

### 2.14 `route` 稳定崩溃（0xC0000005）的根因与绕行流程（2026-11-02）

**现象**：分步流程（`import_db → place → legalize → route → bitgen`）中，`route` 每次都在 `Route runs in 16 thread(s)` 之后 coredump，退出码 139；换回 `syn_v15` 的旧网表同样崩，排除 RTL 因素。

**根因（两条，叠加）**：

1. **僵死工程锁**：`td_project/.lock.f` 里记录的 PID 是崩溃后残留的 `td.exe`（GUI 子进程）。`route` 需要重新打开工程，撞上该锁就崩；而崩溃又再派生新的残留 `td.exe`，形成"每跑必崩、越崩越死"的循环。
   证据：`cat .lock.f` 里的 PID 与 `Get-Process td` 的 PID 完全一致；清掉锁 + 结束该进程后，route 立刻正常。
2. **并行布局布线互踩**：两个 `td_commands_prompt` 同时跑 phy 时，两个进程在同一秒内（相差 2s）都在 `legalize_phy_inst` 之后的 `report_qor` 处 coredump。**必须串行**。

**绕行（现用流程）**：改用官方 `DefaultFlow.tcl` 的**单进程**链路（`read_design → opt_rtl → opt_gate → opt_place → opt_route → bitgen`），综合与布线在同一进程内完成，全程只开一次工程，不再触碰锁竞争。

需补两个坑才能跑通：

- `settings.cfg` 必须补齐 `arr_filter`/`arr_pwns`/`arr_cong`/`arr_rwns`/`drHoldFix` 这 5 个流程控制变量（综合阶段生成的 cfg 只有综合字段），否则 `opt_place` 结束时 `can't read "arr_filter": no such variable`；
- **不要**写 `set cpcList ""`：`if { [info exists cpcList] }` 对空串判定为真，会执行 `import_chipprobe_config ""` 并报 `KIT-8211 ERROR: Please specify a cpc file(*.cpc).`，把 `bitgen` 挡在门外。

**附带收益**：`_pr.db` 已导出后，可用极短脚本单独补出 bit，省掉十几分钟布线：

老 phy 脚本"route 时 `fix_hold off`、route 后再 `fix_hold`"的结论一致。

已固化为可复现脚本：`src/td_project/SingleFlow.tcl`（route 段强制 `fix_hold off` → `route` → `fix_hold` → 恢复参数 → bitgen，结尾 `exit` 避免停在 `td >` 交互 shell；并去掉易崩的 `report_qor`）。用法：把 `settings.cfg` 放在脚本同目录，`td_commands_prompt.exe SingleFlow.tcl`。

### 2.15 横向错位的静态排查结论（2026-11-02）

用户反馈"错位比例自始至终固定"，这是**常量相位偏移**特征，不是随机误码。逐环节核对结果：

| 环节 | 结论 | 依据 |
|---|---|---|
| 写基址 / 读基址 | **640 字对齐，垂直偏移 92 行** | `VID_TOP_OFF = 58880 = 92×640`，`58880 mod 640 = 0`；`BUF3+58880+189440 = 1169920` |
| 读通道 | 从基址**顺序**读满 `read_len`，不逐行回卷 | `frame_fifo_read.v`：`S_ACK` 锁存基址，之后纯 `+1` 推进 |
| 写通道 | 严格 `+1` 顺序推进，无翻转（视频路径 `i_vflip=0`） | `frame_fifo_write.v`：`App_wr_addr_r <= App_wr_addr_r + 1` |
| 行缓冲读写指针 | `f_col` 与 `p` 均为 0..319，严格对应 | `video_frame_fill.v` |
| 写口字流 | 与期望 2 倍放大图**逐字一致**（仅颜色低位不同） | `diff sim/e2e_out.txt tools/video/e2e_exp.hex`，长度均 189440 |
| 帧节奏与回卷 | 41.6667ms 精确、4 帧后正确回卷 | `tb_frame_rate` |
| SDRAM 容量 | `row[10:0]+bank[1:0]+col[7:0]` = 2M 字，最坏占用 1169920 字，**不溢出** | `include/global_def.v` `ADDR_WIDTH=21` |
| SPI 读字节计数 | token 不计入，`byte_cnt 0..511` 恰好 512 数据字节 | `sd_card_cmd.v` `S_READ` / `block_read_valid` |

**结论**：当前 RTL 的**数据通路不存在产生常量横向偏移的机制**，全部可仿真环节均已逐字验证通过。剩下的唯一未验证环节是 SD 物理层读回的字节是否等于文件内容。为此在 OSD 状态区第 4 行加了自证位：

- `OK` = 最近一帧源像素数恰好 `320×148 = 47360`（`video_frame_fill.o_frame_ok → i_vok`）；
- `NG` = 像素数不符，SD 读回字节数不对。

判读口径：`NG` → 问题在 SD/SPI 物理层（下一步降 SPI 时钟）；`OK` 且仍错位 → 问题在 SDRAM 读回或显示时序，需做含 SDRAM 模型的整屏仿真。

### 2.16 视频吞吐恢复（CMD18 流式读）+ 停滞看门狗 + SW4 全屏告警改版（2026-11-02）

**① 根因：201 条 CMD17 的 `tAC` 把一帧拉长到 >100ms**。上一轮为排查数据正确性把视频读退回"一扇区一条 CMD17"，数据字节全对，但吞吐崩了：

| 项目 | 数值 |
|---|---|
| 每帧扇区数 | 201（185 视频 + 16 音频） |
| 纯数据时间 @25MHz SPI | 201 × 512 × 8 / 25MHz = **32.9ms** |
| SD 卡命令响应 `tAC` | 100~300µs（**每次命令**，与数据量无关） |
| 201 次 CMD17 附加开销 | 20~60ms |
| 实际每帧耗时 | **>100ms ≫ 41.67ms 帧周期** |

后果：视频写口来不及提交整帧，显示侧在写了一半的 bank 上按 vs 切换（横向错位 + 彩条），音频 FIFO 供不上 48kHz 消耗（欠载 → 电流声）。

**修复：恢复 CMD18 多扇区流式读**（`sd_card_cmd` 的流终止已由 5.1 节的 CMD12 补齐，可以安全使用）：

- `egv_reader` 新增 `batch_size(run_r, frame_r)` = `min(段剩余, 帧剩余)`，`S_FWAIT` 起帧时用它设置 `o_sd_count`；**一帧内通常只发 1 条 CMD18**，仅当 EGV 物理段边界落在帧内时提前结束本批，下一批的起点/长度在段边界那拍更新；
- 一帧 201 扇区 ≈ 32.9ms 数据 + 1~2 次命令开销 ≈ **34~36ms < 41.67ms**，写口有 5~7ms 余量；
- 读核 `sec_left` 只在 `S_WAIT_READ_WRITE` 锁存，批内客户端改 `sd_sec_read/addr` 无副作用；读端 `S_READ→S_READ_END→S_READ_WAIT→S_READ_WAIT2→S_WAIT_READ_WRITE` 仍留 ≥3 拍给客户端更新地址（5 节的约束不变）；
- 容器头读取与末帧收尾仍是单扇区，不受影响。

**①b 段边界批长的时序修复（v20）**：`min(段剩余, 帧剩余)` 原来在 read_end 那拍用 `run_rem_n`（20bit 减 1 + 跨段 mux）现算，TD 报 `run_rem → o_sd_count` **10.1ns / SWNS -403ps（7 FEPs）**——这是 v19 唯一的时序违例，全部落在 `sd_card_clk` 域。改法：

- `batch_size` 先用 `|run_r[19:16]` 判断 20bit 段剩余是否一定大于 16bit 帧剩余（帧剩余 ≤201），把 20bit 比较器降到 16bit；
- 段最后一扇区的整个 512B 传输期间 `run_rem` 恒为 1，有 500+ 拍预算把下一批长度算进 `batch_nx_q`；read_end 那拍只做 `o_sd_count <= batch_nx_q`（寄存器到寄存器）；
- 下一段长度/起点改为 `nxt_len_q/nxt_rp_q` 寄存器，进入当前段时预装。`run_len_next/rp_next/phys_nx/run_rem_n` 因此只依赖寄存器，跨段那拍不再有"段表 4:1 mux + 20bit 比较"的组合链；

**①c 仿真器陷阱（记下来避免再踩）**：`tbl_len/tbl_rp` 读的是 `rt_len/rt_rp` 存储器。把它们放进**连续赋值**里调用时，ModelSim 不会在存储器/`mode_sel` 更新后重算该线网（`run_len_next` 一直停在复位时的 M_CONST 值），而放在 `always` 块里的同一调用按拍取值是正确的。实卡容器与编译期常量一致，所以这个陈旧值恰好等于正确值、此前从未暴露；`tb_egv_reader_rt` 的合成几何（段长 10/100/493）才把它照出来。v20 起跨段字段全部寄存器化，这类陈旧风险也随之消失。

### 2.17 v20 上板反馈的离线定位：SPI MISO 采样点落在数据窗口末端（2026-11-02）

**① 上板现象（v20 bit，用户实测）**：SW3 拉高 + K1 后先花屏数秒，`FRAM` 约 `00400` 后花屏变成正常画面，**但整幅画面仍带大量彩条**（大部分区域可见、可辨认）；每轮循环回到开头同样先花屏一段时间；**视频音轨自始至终是电流声**，只是在 `FRAM 400+`、画面正常那一刻音色有过一次变化，之后仍是电流声。

**② 先排除容器与 RTL**（本轮全部用证据说话，避免再猜）：

| 检查 | 方法 | 结论 |
|---|---|---|
| 卡上容器是否与本地副本一致 | `sim/real_mem.hex`（卡上前 416 扇区）与 `sd_context/VIDEO.EGV` 前 212992 字节逐字节比对 | **完全一致**，本地副本可信 |
| 容器头/段表 | 直接解 512B 头 | magic `EGV1`、ver 2、**1928 帧**、3 段 `(0,256,47360)(256,385024,513280)(385280,2249,905216)`，与读核运行时段表一致 |
| 画面内容 | `tools/video/egv_dump_frames.js` 解帧 0/30/100/300/399/400/450/600 → PNG | 帧 0~30 全黑（容器本身如此），帧 100 起是正常老片画面，**容器里没有任何彩条/彩屏** |
| 音频内容 | `tools/video/egv_audio_check.js` 解帧 0/1 音频 | 帧 0~59 是数字静音，帧 60 起是真实语音波形（RMS 1300~4100）；按字节交换解读会把波形压成噪声，说明**小端解读正确** |
| 视频/音频 RTL 链路 | 逐模块复读 `egv_reader` / `video_frame_fill` / `frame_fifo_read/write` / `wr_fin_split` / `egv_audio_fifo` / `wav_i2s_source` / `hdmi_audio_tone_i2s_64fs` | 未找到能产生"整屏彩屏"或"持续电流声"的确定性缺陷 |

结论：**卡上的数据是对的，彩屏/彩条/电流声都是 FPGA 侧产生的**，且同时打在画面和音频上——最符合"SD 读回的字节被采错"这一类物理层问题（画面=16bit 像素错色 → 彩条/彩点；音频=16bit 采样错值 → 爆音/电流声）。

**③ 根因：25MHz SPI 下 MISO 在 DCLK 翻转那一拍被采样，正落在数据窗口末端**

`spi_master` 原来是"产生 DCLK 跳变的那一拍同时采 MISO"：

- DCLK 半周期只有 **20ns**（100MHz/4 = 25MHz）；
- 卡在**下降沿**换数据，规范允许 `tODLY` 最大 **14ns**；
- 再加 FPGA 侧 DCLK 输出延迟（时钟到引脚 ~5~8ns）和 MISO 输入延迟（~3ns），数据真正到达输入寄存器时已经吃掉 20ns 窗口的一半以上；
- 留给建立时间的余量只剩 **0~8ns**（慢卡直接为负）→ 偶发采错位/采错字节，**每错一个 bit 就毁掉一个像素或一段音频样本**。

**修复**：把采样点整体后移一拍（`+10ns`），采在 20ns 数据窗口的正中：

```verilog
// spi_master.v
reg miso_pend;                       // DCLK_EDGE 那拍置位，下一拍才采 MISO
always@(posedge sys_clk or posedge rst)
    if (state == DCLK_EDGE) miso_pend <= (CPHA==0) ? (clk_edge_cnt[0]==0)
                                                   : (clk_edge_cnt[0]==1);
    else                    miso_pend <= 1'b0;
...
else if (miso_pend) MISO_shift <= {MISO_shift[6:0], MISO};
```

- 建立时间由 `0~8ns` 抬到 **`6~18ns`**，且距下一个下降沿仍有 10ns（不会撞上卡换数据）；
- 状态机与字节节拍**完全不变**，吞吐不变（`tb_sd_timing` 仍是 CMD18 185.7µs/扇区、201 扇区 37.33ms）；
- 低速段（`clk_div=248`，半周期 2.49µs）同样安全。

**为什么不直接降 SPI 时钟**：下一档是 16.67MHz（`clk_div=1`），201 扇区 ≈ 50ms > 41.67ms 帧周期 → 24fps 保不住、音频 FIFO 立即欠载，等于用一个已知问题换两个新问题。25MHz + 采样点居中才是唯一不牺牲帧率的解法。

**④ 仿真模型补上卡输出延迟（重要）**：原卡模型 `assign SD_MISO = txb[7]` 是**零延迟**，等于假设卡在下降沿瞬间换好数据——这正好掩盖了采样点问题（零延迟下旧采样点当然也对）。`tb_sd_timing` / `tb_menu_boot` 改为：

```verilog
wire #15 SD_MISO_d;  assign SD_MISO_d = txb[7];  assign SD_MISO = SD_MISO_d;
```

### 2.18 换卡后 `FRAME 00000` + `V:NG`：容器被拷到扫描窗口外（2026-11-02）

**① 现象**：SW3 + K1 后资源面板一直显示 `FRAME 00000`、`VIDEO: RUN`、右侧 `NG`，无画面。

**② 直接读卡定位**（`tools/video/egv_locate.js`，读物理盘）：

```
MBR 分区起始 LBA = 32768（16.0MB）
exFAT: FAT@49152  簇堆@65536  根目录簇=4  簇大小=256扇区(128KB)
VIDEO.EGV: 198414848 字节 = 387529 扇区，起始簇 305 → LBA 143104
物理段数 = 1   （簇 305..1818，整文件物理连续）
头扇区魔数 = "EGV1"，n_runs=3，但段表 phys = 47360 / 513280 / 905216（旧位置）
```

**③ 因果链**：

1. `bmp_read` 扫描窗口是 `SCAN_MAX_SECTOR = 131071`（64MB），且**每 8 扇区只读 1 个扇区**；
   容器头在 **LBA 143104（69.9MB）**，越出窗口 → `egv_found = 0`。
2. 回退到编译期 `EGV_BASE_LBA = 47360` 读头；该扇区现在是**全 0**（MBR 分区基址 32768
   把旧卡布局整体推后，这里落在卷保留区与 FAT 之间的空白）→ 魔数校验失败。
3. `egv_reader` 的模式判定 `M_RT → M_CONTIG → M_CONST → M_NONE`：
   - 段表物理地址 ≠ 发现位置 → 不是 `M_RT`；
   - 头都没读到 → 不是 `M_CONTIG`；
   - `magic_ok && hdr_lba == EGV_BASE_LBA` 也不成立（魔数失败）→ **`M_NONE`**。
4. `M_NONE` 是**主动拒播**：`S_HDR_CHK2` 不进入取流，一帧都不读（设计意图是"绝不拿过期
   段表去读别的扇区"，这正是 2.13 花屏问题的防线）。于是：
   - `vf_frame_end` 永不产生 → `osd_layer` 的 `vid_bcd` 不递增 → **`FRAME 00000`**；
   - `o_frame_ok` 只在 `E_END` 更新，没帧就保持复位值 0 → **`NG`**；
   - `VIDEO: RUN` 来自 `vid_on_v = vid_layer_v & vid_play_v`，只表示"层3 + 已按 K1"，
     不代表真的在读帧。
5. 这也解释了为什么上一版（v20）能出画面：那次卡上容器还在旧位置（或超级软盘布局，
   头在 47360 附近）；这次重新拷贝后文件落到簇 305（BMP + WAV 之后）。

**④ 修复：扫描窗口 64MB → 128MB（`top_tf_hdmi_audio.v`）**

```verilog
.SCAN_MAX_SECTOR (32'd262143),   // 128MB：覆盖 LBA 143104 的容器头
```

- 262143 是 `sd_card_bmp` 里 16 项 `img_sector` 表 **18bit 能表示的上限**
  （262143 = 16#3FFFF）；再往上扩窗口必须先把这些表加宽到 20bit，否则超过
  262143 的图片起始扇区会被截断。
- 扫描开销：窗口内仍按 4KB 步进（17,888 次单扇区读），命中 EGV 后因跳转点
  （143104 + 387529 = 530633）仍越过新窗口，退化为 4KB 步进继续扫到 262143
  ——比原来多约 1.5 万次单扇区读（约 3s），换取对重新拷贝后布局的容忍度。
- 容器头内段表仍是旧位置（`phys=47360`），`phys0_ok=0` 但其余字段
  （ver/w/h/fps/帧数/几何/音频参数、各段之和 = 1928×201 = 387528）全部自洽
  → `M_CONTIG`：从 `hdr_lba+1` 起按整文件连续读 387528 扇区。
  **已用 FAT 链确认该文件只有 1 段（簇 305..1818）**，M_CONTIG 成立。

**⑤ 换卡/重拷后的自检**：跑 `node tools/video/egv_locate.js <盘号> VIDEO.EGV`，
必须满足"4KB 对齐: 是 / 在窗口内: 是 / 物理连续: 是"。若"物理连续: 否"，
M_CONTIG 会读到别的文件的数据（又是彩条），此时应重新整理卡（先拷 VIDEO.EGV 或
格式化后整批拷贝）再测。

## 5. 已定位的协议约束（读核与客户端）

`sd_card_sec_read_write` 的“下一请求”是在 `S_WAIT_READ_WRITE` 里采样 `sd_sec_read`/`sd_sec_read_addr` 的，**采样窗口的起点由结束脉冲到客户端的寄存器级数决定**：

- `sec_end_pulse`（读核内部）→ `rd_end_q`（读核输出寄存）→ `bmp_e_q`（`sd_card_bmp` 仲裁分流寄存）= 2 级；
- 客户端因此在结束脉冲后第 3 拍才更新地址，读核必须空等 ≥2 拍（`S_READ_WAIT`/`S_READ_WAIT2`）再进入 `S_WAIT_READ_WRITE`；
- 给结束/数据/有效加流水级时，**必须同步增加这里的空等拍数**，否则每个扇区都会重发上一条命令（表现：扫描停在扇区 0、LOADING 不消失、装载超时重试把 `load_busy` 顶死导致视频黑屏）。

`tb_sd_timing` 的 `+LAG`（客户端地址滞后拍数，默认 1）就是这条约束的守卫：把读核的空等态减回一个，`+LAG=1` 立刻 FAIL 并打印 `DATA ERR sec=1 ...`。

## 5.1 已定位的协议约束（CMD18 流终止与 EGV 扫描跳转，2026-11-01）

**CMD18 必须以 CMD12 终止**：SPI 模式下流中途抬 CS 只是"暂停"而非终止，真实卡仍停留在数据发送态，之后的命令在 DO 上只能读出数据残留、得不到合法 R1 → 只有视频客户端使用 CMD18，故长期表现为"图片/扫描正常、唯独视频从未上板成功"。修复在 `sd_card_cmd` 内部：最后一块读完 → `S_STOP_CMD` 发 CMD12（CS 保持低、无视 DO）→ `S_STOP_BUSY` 等 DO 回 0xFF（busy 释放，64 字节超时兜底）→ 才进 `S_READ_ACK` 给 `block_read_req_ack`。`tb_sd_timing` 卡模型已改为真实语义（CS 抽升不清 `is_stream`、流中检测 CMD12、流未停时新命令只回 0x00），反证：删掉 `S_STOP_CMD` 路由后 TB 在第二批 CMD18 处死锁超时。

**EGV 扫描跳转越界不得提前收工**：实卡 EGV@47360（total_bytes 198MB → 跳转点 434889）越过 scan_max(131071)，旧版在此直接 `scan_done`，而 WAV@58624 落在容器物理跨度内的间隙（容器 3 段不连续）→ WAV 永远扫不到 → `wav_found=0` → 音频回退测试音；另有 4 张 BMP（47872/49920/53248/55296）同样漏扫。修复：跳转越界时退化为 4KB 对齐步进继续扫（多 ~1s），窗口内文件全部能被发现。`tb_bmp_egv_scan` 场景 A 已改为该行为的回归（EGV 之后 WAV@40 + BMP@416 必须被发现，共 54 次读）。

**egv_reader 运行时段表深度 = 4**（与 `mp4_to_egv.py` 的 `MAX_RUNS` 一致）：8 段版本的 8:1 段表 mux 把 LUT 推到 16678、切片 98.3%，P&R Setup -1.28ns 不收敛；裁回 4 段后 LUT 16098（82.1%）、切片 95.8%，seed 3 收敛于 Setup +126ps / Hold +21ps / 0 FEP。实卡容器 nruns=3，超过 4 段的封装按"整文件连续"回退或拒播（绝不读错扇区）。
